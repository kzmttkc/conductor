## 2. 今回特に評価する点

### 2.1 実行レイヤーの二段構え
- LLMキーがある場合 → 本物の `generateText` + tools
- ない場合 → structured research + live web search
- どちらでもエスカレーションとレポート生成まで到達する設計は非常に実用的

### 2.2 公開デモ戦略
- `/demo` ワンクリック
- `/demo/moment`（Needs Youの瞬間を共有）
- OG画像・GIF・storyboard.json
- Build in Publicにそのまま使える資産が揃っている

これは「最初の30人」を集めるための最強の武器になる。

### 2.3 スキーマの進化
- `artifacts`（成果物）
- `usage_stats`（利用量）
- Realtime対象の拡大

指揮の結果が永続化され、課金の根拠にもなる構造になった。

### 2.4 エスカレーションの「判断」が本物になった
LLMが `escalate_to_human` ツールを自ら呼ぶ設計。  
条件分岐だけでなく、モデルの判断で人間に渡す流れができた点が大きい。

## 3. 残る厳しい指摘

### 高優先度（P0）

**P0-1. 本番Supabaseパスの実行がまだ薄い**
- Demo Modeは非常に完成している
- 一方で `NEXT_PUBLIC_DEMO_MODE=false` 時のエージェント実行・ログ書き込み・artifact保存のE2Eが十分に検証されているか不明
- Realtime + RLS + 複数ユーザーでの動作確認が必要

**P0-2. 権限の「編集体験」が指揮の核として弱い可能性**
- 型と実行時チェックは良くなった
- しかしエージェント詳細画面で「このツールはRequire Approvalに変更」を即座にでき、それが次の実行に効く体験が、仕様で求めた「指揮感」の中心
- UIがまだログ中心になっていないか要確認

**P0-3. マルチエージェント連携がまだ弱い**
- Research Crewは3体起動できる
- しかしScout → Synthesizer → Verifier の**成果物受け渡し**が明示的でない
- 現状は並列に近い独立実行の可能性が高い
- 「チームを指揮している」感を出すには、前段のartifactを次段が読む流れが欲しい

### 中優先度（P1）

**P1-1. レポート品質のばらつき**
- structured fallback時のレポートとLLM時のレポートで差が大きい
- Verifierの「検証」が表面的になりやすい

**P1-2. エラーからのリカバリ導線**
- status=error になった後の「再実行」「権限を緩めて再実行」が弱いと指揮感が削げる

**P1-3. 使用量の可視化**
- `usage_stats` は存在するが、設定画面やダッシュボードでの見せ方が弱いと課金動機に繋がらない

**P1-4. Stripe本実装**
- パッケージは入ったが、Checkout → Webhook → plan更新の完全フローはまだstubの可能性

### 低優先度

- テンプレートの追加（Content / Competitor Watchなど）
- モバイル最適化
- チーム機能は不要（ソロ特化を崩すな）

## 6. 監査結論（v2）

前回の「よくできたデモ」から、**「実際に指揮して成果物を得られるプロダクト」**へと明確に進化した。

特に以下の3点が決定的に良くなった：
1. 実LLM（または高品質fallback）での実行
2. artifactsによる成果の永続化
3. 公開デモとソーシャル資産

残る最大のギャップは「本番環境での信頼性」と「マルチエージェントの連携感」「権限を触って指揮している感覚」の3点。

これらを潰せば、Starter課金を自然に取れる状態になる。

**推奨次アクション**
1. この監査を受けてP0を潰す
2. 公開デモURLを固定して発信開始
3. 1週間後に「本番でResearch Crewがレポートを残す」状態をゴールにする

Conductorは今、製品として「形になった」。  
あとは「信頼して毎日使えるか」の仕上げである。
